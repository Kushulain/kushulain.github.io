Shader Breakdown · Hanahana (2018)

Fake Skin SSS
via a Shadow Buffer Hack

Real-time Subsurface Scattering approximation for hands and skin in Unity's Built-in Renderer — without any post-process stack, geometry shader, or thickness texture.

Unity 5 · Built-in Pipeline HLSL / CG Shadow Map Screen-Space Skin Rendering

01 — Overview

Subsurface Scattering (SSS) is the optical phenomenon that makes skin translucent: hold your hand up to a strong light source and you'll see red-orange glow through the fingers. It's one of the defining qualities that separates a convincing skin render from a painted plastic surface.

Hanahana (2018) was a performance piece rendered in Unity 5, Built-in Pipeline. No HDRP, no post-process stack. The project featured hundreds of animated hands filling the frame — making a traditional SSS approach (geometry pre-pass, thickness textures, multi-layer diffuse profiles) completely impractical.

The technique described here is a deliberate hack: it repurposes an existing rendering buffer — the screen-space shadow collection pass — to smuggle a SSS proxy value all the way through to the material shader. No extra passes, no extra render targets.

02 — The Pipeline

Unity's shadow pipeline works in three stages. We intercept the second one.

Stage 1 Shadow Map
depth from light POV
→
Stage 2 · Our hack Screen-Space Shadow Buffer
R=G=A : hard shadow · B : SSS proxy
→
Stage 3 Material Shader
reads shadow.z for SSS

The screen-space shadow buffer is a full-screen RGBA render texture. Normally all four channels contain the same shadow attenuation value (0 = fully in shadow, 1 = fully lit). By writing a different value into the blue channel, we get a free communication channel to any material that samples this buffer — at zero additional rendering cost.

Key insight: this is a per-pixel, full-screen operation. The cost is completely independent of scene complexity, mesh count, or draw call count. It runs once, exactly like a post-process effect.

03 — Part 1: Shadow Collection Pass

The shadow collection pass is implemented in Internal-ScreenSpaceShadowsCustom.shader. Drop it in your project's Resources/ folder and Unity automatically picks it up over the built-in version.

Inside frag_pcfSoft, after computing the standard hard shadow (shadow via PCF7×7), we compute a second value called shadow2 which will become the blue channel.

The Core Idea

Instead of sampling the shadow map at the fragment's world position, we sample it at nearby world positions offset along the light direction. This is the translucency simulation: a point that is in shadow might still be "reachable" if you peek from a slightly different angle through thin geometry.

On top of that, the samples are spread in a disk in the camera's tangent plane (spanned by the camera right and up vectors), which blurs the shadow boundary spatially — mimicking the scattering radius under skin.

Why a Hexagonal Pattern?

The naive approach is a cross pattern (±X, ±Y), but that leaves 45° blind spots — visible on rounded geometry like fingers seen in diagonal. A hexagonal pattern (6 points at 60° intervals) reduces the maximum angular error from 45° to 30°, which is the optimal tradeoff for 6 samples on a disk.

Internal-ScreenSpaceShadowsCustom.shader · frag_pcfSoft 
// Camera axes in world space — these define our sampling disk plane
float4 xeye = float4(mul((float3x3)unity_CameraToWorld, float3(1,0,0)), 0.);
float4 yeye = float4(mul((float3x3)unity_CameraToWorld, float3(0,1,0)), 0.);

// Offset along the light direction = peek through thin geometry (~1.5 cm)
lightDir.xyz *= -0.015;

float blurSize = 0.05;          // disk radius in world units
float hBlur = blurSize * 0.5;   // cos(60°)
float dBlur = blurSize * 0.866; // sin(60°)

// Isotropic hexagonal pattern: 6 samples at 60° intervals + weighted center
// Avoids the 45° blind spots of a cross pattern (±X, ±Y)
half shadow2;
shadow2  = PCF3x3(wpos + lightDir + xeye * blurSize);                     // 0°
shadow2 += PCF3x3(wpos + lightDir + xeye * hBlur + yeye * dBlur);          // 60°
shadow2 += PCF3x3(wpos + lightDir - xeye * hBlur + yeye * dBlur);          // 120°
shadow2 += PCF3x3(wpos + lightDir - xeye * blurSize);                     // 180°
shadow2 += PCF3x3(wpos + lightDir - xeye * hBlur - yeye * dBlur);          // 240°
shadow2 += PCF3x3(wpos + lightDir + xeye * hBlur - yeye * dBlur);          // 300°
shadow2 += PCF3x3(wpos + lightDir) * 2.0;                               // center ×2
shadow2 /= 8.0;  // normalize: 6 × 1.0 + 1 × 2.0 = 8

shadow2 = pow(shadow2, 0.8);
shadow2 = lerp(shadow2, shadow, 0.2); // blend a little hard shadow back in
shadow2 *= shadow2;                      // square: deepen the effect non-linearly

// R, G, A = standard shadow  ·  B = SSS proxy
return fixed4(shadow, shadow, shadow2, shadow);

Note: PCF3x3 above is shorthand for UnitySampleShadowmap_PCF3x3(GET_SHADOW_COORDINATES(...), bias). The actual shader uses that full form with cascade weights.

Performance Cost

Unity's PCF functions use hardware bilinear shadow fetches. Here's how our approach compares:

Configuration Calls Hardware taps (approx.)
Unity default soft shadow 1× PCF7×7 ~16
Our base shadow (unchanged) 1× PCF7×7 ~16
Our SSS ring 7× PCF3×3 ~28
Our total 8 calls ~44 vs 16 vanilla

That is roughly 2.75× more expensive than vanilla Unity soft shadows. However, this pass runs once per frame regardless of how many objects or draw calls are in the scene — so the absolute cost stays bounded and predictable. For a project like Hanahana with hundreds of mesh instances, this is clearly the better trade-off compared to per-material thickness textures.

04 — Part 2: The Material Shader

The material shader is a custom StandardSpecular surface shader with a custom lighting function. It reads the screen-space shadow buffer manually to extract both the regular shadow and our blue-channel SSS proxy.

Reading the Blue Channel

In the surf() function, the screen-space shadow buffer is sampled manually using the pre-computed screen position. The blue component (shadow.z) is stored in a global variable for the lighting function to consume.

Material Shader · surf() 
// Screen-space shadow buffer — sampled manually via pre-computed screen UV
fixed4 shadowSample = UNITY_SAMPLE_SCREEN_SHADOW_F(_ShadowMapTexture, i.screenPos);

// The blue channel carries our hexagonal-sampled SSS proxy
//   0.0  →  fully occluded (or behind thick geometry)
//   1.0  →  directly lit (and spatial neighbors too)
SSS = shadowSample.z;

Angle-Based Modulation

In the custom lighting function, the SSS value is scaled by an angle-based multiplier that approximates two physical phenomena:

  • Backlit translucency: when the camera looks toward the light source (fingers silhouetted against the sun), SSS is maximal. Captured by dot(lightDir, -viewDir).
  • Bounce / ambient wrap: a secondary SSS contribution that is present even when not backlit — simulating indirect scattering.
Material Shader · LightingStandardSpecularCustom() 
// N·L: positive = lit side, negative = shadow side
half dotLight = dot(gi.light.dir, worldNormal);
half back     = min(0.0, dotLight);  // contribution from backlit hemisphere only

// Camera-to-light axis: 1.0 = looking into the light (backlit silhouette)
half lookToSun = dot(gi.light.dir, -viewDir) * 0.5 + 0.5;

// Blend between bounce and backlight strengths.
// pow(lookToSun, 10.0) makes the backlight falloff very tight — only
// activates strongly when the camera is nearly in the sun axis.
float multiplier = lerp(SSS_bounced, SSS_backLight, pow(lookToSun, 10.0));

// Color gradient: thin/occluded areas glow warm; thicker lit areas get near skin tone.
// SSS * SSS makes the transition nonlinear (favors the warm far color).
float3 sssColor = lerp(_SSS_far, _SSS, SSS * SSS).rgb;

// Final contribution — added directly on top of the standard BRDF result
float intensity = SSS * multiplier * saturate(isNail + 1.0 + h + back);
c.rgb += intensity * sssColor * _LightColor0.rgb;

The Color Gradient

Two HDR colors are exposed per hand size category (small / big hands are scaled differently): _SSS (near, bright areas) and _SSS_far (deep/occluded areas). The interpolation key is SSS * SSS, meaning dark-shadowed pixels get the warm, saturated far color — giving fingertips and ear edges that characteristic orange-red glow seen in strong backlighting.

Nail Masking

A small but effective detail: nails have a high blue component in the albedo texture. isNail = smoothstep(0.3, 0.48, albedo.b) extracts a smooth nail mask at zero texture cost. Nails get a different (harder, more specular-like) SSS response, blending into a half-albedo tint instead of the warm skin SSS.

05 — Integration

The technique is easy to drop in, with three steps:

  1. Copy Internal-ScreenSpaceShadowsCustom.shader into your Resources/ folder. Unity picks it up automatically over the built-in version. No configuration needed.
  2. In your material shader, define #define UNITY_SAMPLE_SCREEN_SHADOW_F for stereo compatibility and sample _ShadowMapTexture manually with a pre-computed screen position. Read shadow.z as your SSS input.
  3. Add fullforwardshadows to your #pragma surface directive so Unity always writes the shadow buffer for this object.

Cost reminder: the shadow collection pass runs once per frame, globally. Enabling this effect costs the same whether you have 1 or 10 000 skinned meshes in the scene. In scenes with many instanced objects it's essentially free compared to per-material solutions.

06 — Limitations

  • Screen-space artifacts: the SSS value is computed in screen space, so it can leak at geometry edges where the depth discontinuity confuses the sampling pattern. For hands filling the frame this is barely visible.
  • No true thickness: the technique does not model actual sub-surface path length. The bleed amount is spatially uniform, controlled only by the fixed blurSize and lightDir offset — not by how thick the geometry actually is.
  • Built-in Pipeline only: HDRP and URP handle the shadow collection pass differently. The override shader approach is specific to the Built-in renderer.
  • Blue channel squatting: if any other built-in system ever uses shadow.z for something else, there will be conflicts. In practice, Unity leaves it as a copy of the shadow value — so this is safe.
